# ADR-004: Media Upload and Object Lifecycle

Status: Accepted for first vertical slice
Date: 2026-09-25

## Decision
Media binaries are stored in object storage, while PostgreSQL stores their authoritative metadata and business relationships.

Cloudflare R2 is the selected object-storage target for the first vertical slice.

The client uploads media directly to object storage using a server-authorized upload mechanism rather than streaming large media bodies through the application API.

## Ownership
Media owns:
- media metadata
- upload lifecycle state
- object key ownership
- attachment relationships
- validation status
- cleanup lifecycle

Catalog owns the business meaning of an attached image or audio recording.

PostgreSQL is authoritative for media metadata and attachment relationships.

R2 is authoritative for the binary object itself.

## Upload Lifecycle
The intended lifecycle is:

1. Client creates or updates an offline draft.
2. Sync submits media metadata and requests upload authorization.
3. Server validates authorization and returns the information required for direct upload.
4. Client uploads the binary directly to R2.
5. Client reports successful upload completion.
6. Server verifies the expected object and records the media as available.
7. Downstream AI or catalog processing may consume the media only after the media reaches an accepted server state.

An upload that is interrupted may be retried without creating a second logical media record.

## Object Keys
Object keys must be generated by the server-side ownership boundary.

Keys must not contain unnecessary personal information.

A logical media record and its object key are distinct concepts; replacing an uploaded object must not silently destroy the auditability of the previous state.

## Validation
Server-side validation is required before media becomes usable by downstream processing.

Validation includes applicable file type, size, integrity, ownership, and lifecycle checks.

Client-side validation is an optimization, not a trust boundary.

## Failure and Recovery
Interrupted uploads remain recoverable.

Expired or abandoned upload authorizations must not grant indefinite access.

Duplicate completion requests must be idempotent.

An object that exists without a valid metadata record becomes eligible for controlled orphan cleanup.

A metadata record that references a missing object becomes an explicit repair/error state rather than silently appearing valid.

## Deletion and Retention
Deleting a business attachment first changes the authoritative application state.

Physical object deletion is handled as a controlled lifecycle operation so retries and recovery remain possible.

Retention and purge policies must account for audit, legal, privacy, and operational requirements before permanent deletion.

## Security
Upload authorization must be scoped to the intended authenticated actor and operation.

Clients must never receive broad object-storage credentials.

Uploaded media is treated as untrusted input.

Media processing workers must not assume that file metadata or client-declared MIME types are trustworthy.

## Consequences
Positive:
- Large media does not unnecessarily traverse the API server
- Upload retries are easier to isolate
- Object storage scales independently
- Media lifecycle is explicitly auditable

Negative:
- Upload completion becomes a multi-step workflow
- Orphan cleanup is required
- Client and server must coordinate upload state

## Rejected Alternative
Store media binaries directly inside PostgreSQL.

Reason: the first vertical slice needs reliable handling of photo and voice payloads without coupling large binary storage to transactional business data.
